# 用户鉴权 · VIP · API 配额方案（设计稿）

> 状态：**设计已定方向，代码未落地**（前端登录仍为本地 stub）  
> 更新日期：2026-08-05  
> 关联：[PROJECT_PLAN.md](../PROJECT_PLAN.md) §1.3 / 里程碑 M6+；产品边界见 `.cursor/rules/project-scope.mdc`  
> 目的：官方 API 配额有成本；后续能力向「用户身份 + VIP 额度」靠拢，避免全民无限触发官方拉取。

---

## 1. 目标与原则

### 1.1 要解决什么

- 谁触发了官方调用、消耗了多少配额，要可审计。
- 超额与「即时性」由用户/VIP 承担；公共底座仍由平台统一拉取，多人共享读库。
- 额度用尽后产品仍可用（只读本地），而不是整站报废。

### 1.2 原则

| 原则 | 说明 |
|------|------|
| 公共池 vs 用户池 | **定时任务 / 初盘冻结 / 一级联赛缺盘 / 临场 30 分钟一次 / 按日赛果** → 平台公共池。**手动 sync、勾选非一级联赛补盘、详情按需补拉、PC「刷新官方」** → 用户池（计额度）。 |
| 一人拉、多人读 | 同一日窗 / 同一动作，已有进行中的 sync（`status=running`）或本地已新鲜时，不重复打官方；用户额度扣的是「触发权」，不是把每一次 HTTP 简单乘以在线人数。 |
| 先身份、后 VIP、再支付 | 真登录 → 动作级计量（可先只记日志）→ 档位限额 → 支付/订阅。 |
| Key 永不进前端 | 与现网一致；前端只调本项目 `/api/v1`。 |
| 非直播站 | 不做滚球轮询；VIP 不卖「实时比分」，卖「更多合法赛前补拉与更高额度」。 |

## 2. 角色与权益（产品分层）

额度数字为**示意**，上线前按套餐与官方日配额再定。

| 档位 | 身份 | 可读 | 可触发官方（用户池） | 其它 |
|------|------|------|----------------------|------|
| 游客 | 未登录 | 本地已有列表 / 详情 / 赛果（只读） | 默认禁止，或极低日限 + 强提示 | 收藏等仅本机；不云同步 |
| 登录免费 | 已注册登录 | 同上 + 账号侧能力 | 小额日限（如手动 sync N 次、详情补拉 M 次） | 收藏云同步、计算器 |
| VIP | 有效订阅 / 权益标记 | 同上 | 更高日限；非一级联赛补盘；PC「刷新官方」；更长历史窗口等 | 额度用尽 → 降级为只读本地，文案说清 |

**不建议**把 VIP 做成「每人一套 ML 模型」；训练与公共推理继续服务端共享。VIP 更适合绑：**触发官方的权利、额度、联赛补盘范围、刷新入口**。

## 3. 配额计量模型

### 3.1 计量动作（建议枚举）

| `action` | 含义 | 典型入口 | 池 |
|----------|------|----------|----|
| `sync_day` | 按日/窗强制官方赛程（+ 默认盘口策略） | 会话首次 sync、下拉刷新、PC 刷新官方 | 用户（手动）/ 公共（定时） |
| `odds_only_league` | 仅补拉指定联赛盘口 | 勾选 `extra` 联赛 | 用户 |
| `fixture_enrich` | 单场详情缺包补拉（阵容/伤病/H2H 等） | 详情打开按需 | 用户 |
| `final_odds_window` | 开赛前 30 分钟临场盘 | 调度器 | **公共** |
| `capture_results_day` | 按日回写赛果 | 调度 / 赛果页策略 | **公共** |
| `scheduled_fixtures_sync` | 06/12/18 等定时全量窗 | 调度器 | **公共** |

公共池动作**不扣**用户额度，但应写入**平台配额日志**（监控日余量）。

### 3.2 账本（建议表）

`quota_ledger`（名可再定）每条至少含：

- `user_id`（可空 = 系统/公共）
- `action`、`scope`（如 `date` / `league_id` / `fixture_id`）
- `estimated_requests` / `actual_requests`（若可知）
- `status`：`accepted` / `denied` / `deduped`（命中 running 或已新鲜未打官方）
- `created_at`

用户侧日汇总：`user_quota_daily(user_id, day, used, limit, plan)`。

### 3.3 扣费规则（建议）

1. 请求进入需打官方的路径前：`can_spend(user, action, cost)`。  
2. 若全局已有同类 sync `running` → 返回现有 `running`，记 `deduped`，**不扣**或扣「触发尝试」的极低成本（产品二选一，推荐不扣）。  
3. 若本地已满足 TTL / 已有初盘且策略为「只补缺」→ 可不打官方，不扣或少扣。  
4. 真正发起官方 HTTP 前扣减（或预留 + 完成后结算），失败可回滚预留。  
5. 额度用尽：HTTP `402` 或 `429` + 业务码 `quota_exhausted`；前端提示「本地仍可用，无法再向官方拉取」。

## 4. 鉴权与会话

### 4.1 现状

- 前端：`LoginModal` 等为**本地会话 stub**，无后端 `/auth`。  
- 官方 Key：仅后端 `secrets.local.env`。

### 4.2 目标形态（尚未实现）

- 后端：注册 / 登录 / 刷新令牌（或 session cookie）；`users`、`sessions`（或 JWT + refresh）。  
- VIP：`user_entitlements` 或 `subscriptions`（`plan`、`expires_at`）。  
- 受保护路由：手动 `POST /fixtures/sync`、odds_only、详情 enrich 等校验身份 + 额度。  
- 只读列表 / 已落库详情：可继续匿名（或登录增强），与「触发官方」分离。

密码与密钥规范遵循现有 secrets 规则；生产再定 OAuth（可选，非必须首版）。

### 4.3 用户私有数据（留坑 · 无痛衔接）

收藏、计算器方案等**按用户隔离**的数据，在真登录落地前也要按「以后有 user_id」来写，避免全民共用一张表。

| 约定 | 说明 |
|------|------|
| `user_id` 可空 | `NULL` = 登录前的本机单租户桶（当前行为）；登录后写入真实用户 id |
| 查询必带作用域 | `owner_is(column, user_id)`（`app/services/user_scope.py`）；禁止无过滤全表扫私有数据 |
| 鉴权依赖 | `CurrentUserId`（`app/api/deps_auth.py`）现恒为 `None`；接 JWT/session 时只改这一处 |
| 首登迁移 | 可选：把该设备上 `user_id IS NULL` 的收藏/方案认领到当前账号一次，再禁止匿名写 |
| 收藏 PK | 现为 `fixture_id`（单租户够用）；多用户时改为 `(user_id, fixture_id)` 或代理主键 |

已挂钩的表/接口：`favorite_fixtures.user_id`、`bet_plans.user_id`，以及 `/favorites`、`/bet-plans`。

**原则**：未登录时**不假装**做云同步或跨设备私有；新功能可以先落地业务，但私有数据路径必须过 `CurrentUserId` + `owner_is`，登录完善后只接身份、不改业务语义。

## 5. 与现有同步链路的对齐

| 现网行为 | VIP 方案下 |
|----------|------------|
| 浏览器会话首次自动 `POST /fixtures/sync` | 游客：跳过或极严限；登录用户：扣用户池小额；也可改为「仅定时公共同步 + 手动才扣额度」 |
| 手机列表下拉刷新 | 登录/VIP 手动 sync，计 `sync_day` |
| PC 无下拉 | 规划顶栏/工具条「刷新官方」（VIP 或登录特权），同一后端计量 |
| 勾选非一级联赛 | `odds_only_league`，登录以上；VIP 更高日限 |
| 定时 06/12/18、临场 30 分钟、赛果回写 | 保持公共池，不绑单用户 |
| 初盘冻结 / 即时盘展示去重 | 数据语义不变；与鉴权正交 |

**推荐演进**：公共数据主要靠调度保证「新鲜底座」；用户手动 sync 变成明确的付费/额度行为，而不是每个 F5 都打官方。

## 6. 前端体验要点

- 「我的」：登录态、当前档位、今日剩余额度、VIP 到期。  
- 触发官方前：可预估或展示「将消耗 1 次同步」。  
- 额度用尽：列表/详情不空白，禁用刷新入口并说明原因。  
- PC「刷新官方」与手机下拉共用同一 API 与额度。  
- 游客与登录权益差异在 UI 上可发现（勿静默失败）。

UI 细则后续写入 [frontend/FRONTEND_UI_SPEC.md](../frontend/FRONTEND_UI_SPEC.md)；本文件以业务与后端契约为主。

## 7. 后端落地顺序（实施清单）

代码按此顺序迭代，**当前仓库尚未开始**：

1. **用户表 + 真登录 API**（替换前端 stub；填充 `CurrentUserId`）  
2. **私有数据认领**：`favorite_fixtures` / `bet_plans` 的 `NULL → user_id` 一次性迁移；收藏 PK 升级为复合键  
3. **`quota_ledger` + 中间件/依赖注入**（先 `log_only` 模式，不拦截）  
4. **动作接入**：`sync` / `odds_only` / `fixture_enrich` 打点  
5. **档位限额配置**（环境变量或 DB）：游客 / free / vip  
6. **拦截模式**：额度不足拒绝；公共调度路径豁免  
7. **前端**：剩余额度展示、PC 刷新入口、用尽态  
8. **支付 / 订阅**（最后）：发卡或第三方支付写 `entitlements`

## 8. 风险与约束

| 风险 | 应对 |
|------|------|
| 同账号刷 sync | 日限 + 冷却 + 已有 `_sync_lock` / `running` |
| 公共 sync 与用户抢配额 | 调度错峰；用户池设软上限；监控官方日余量 |
| 用户以为「VIP=实时比分」 | 文案与产品边界写清：赛前分析，非直播 |
| 计量不准导致客诉 | 账本可查；`deduped` 与真实 HTTP 区分 |
| 免费用户过多拖垮公共池 | 公共池只覆盖一级联赛 + 固定窗；其余必须用户触发 |

## 9. 验收标准（本方案「完成」时）

- [ ] 未登录无法无限制触发官方 sync（策略按 §2）  
- [ ] 登录用户额度可查、可扣、用尽可理解  
- [ ] VIP 与免费在额度/入口上可区分  
- [ ] 定时任务不误扣用户额度  
- [ ] 账本能回答「今日谁、因何、打了多少官方」  
- [ ] Key 仍仅存后端；前端无官方 Key
