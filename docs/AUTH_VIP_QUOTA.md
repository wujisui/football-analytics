# 用户鉴权 · VIP · API 配额方案（设计稿）

> 状态：**真登录已落地（账号/邮箱 + 密码，httpOnly cookie 会话）**；VIP / 支付 / 平台配额账本仍为设计稿
> 更新日期：2026-08-05  
> 关联：[PROJECT_PLAN.md](../PROJECT_PLAN.md) §1.3 / 里程碑 M6+；产品边界见 `.cursor/rules/project-scope.mdc`  
> 目的：官方 API 配额有成本；定时公共池拉赛程/盘口/赛果，详情按点击补缺落库后多人复用；列表路径不放大官方请求。

---

## 1. 目标与原则

### 1.1 要解决什么

- 六个固定同步批次消耗了多少官方配额，要可审计。
- 赛程/盘口/赛果由平台统一拉取；详情缺包时按点击补拉并落库，后续读者复用。
- 官方配额用尽时产品仍可读取最近一次落库数据。

### 1.2 原则

| 原则 | 说明 |
|------|------|
| 单一公共池 | 每天 00/06/11/16/19/22 六个固定同步批次统一更新赛程、一级联赛盘口与赛果。 |
| 列表本地、详情按需 | 页面、F5、下拉刷新、筛选只读本地；打开详情缺包时可打官方并落库，不按列表在线人数放大。 |
| 先身份、后 VIP、再支付 | 真登录 → 动作级计量（可先只记日志）→ 档位限额 → 支付/订阅。 |
| Key 永不进前端 | 与现网一致；前端只调本项目 `/api/v1`。 |
| 非直播站 | 不做滚球轮询；VIP 不提供「手动刷官方」入口；日后可把详情补拉或全量预拉纳入用户/VIP 额度。 |

## 2. 角色与权益（产品分层）

额度数字为**示意**，上线前按套餐与官方日配额再定。

| 档位 | 身份 | 公共数据 | 其它 |
|------|------|----------|------|
| 游客 | 未登录 | 本地已有列表 / 详情 / 赛果（只读） | 收藏等仅本机；不云同步 |
| 登录免费 | 已注册登录 | 同上 | 收藏云同步、计算器 |
| VIP | 有效订阅 / 权益标记 | 同上，不增加官方刷新权 | 更长历史窗口、账号侧增强等 |

**不建议**把 VIP 做成「每人一套 ML 模型」；训练、公共推理和官方数据同步继续服务端共享。

## 3. 配额计量模型

### 3.1 计量动作（建议枚举）

| `action` | 含义 | 典型入口 | 池 |
|----------|------|----------|----|
| `scheduled_fixtures_sync` | 全量赛程 + 一级联赛盘口 + 赛果 | 每天六个固定时点 | **公共** |
| `detail_package_enrich` | 单场展示包按需补拉 | 用户打开详情 | **公共落库 / 日后可计用户额度** |
| `subscribed_full_detail` | 已订阅完整批次为今天/明天热门未开赛缺包场次预拉详情 | 管理员「订阅」开关；配额耗尽即停 | **公共；仅已订阅** |


公共池动作**不扣**用户额度，但应写入**平台配额日志**（监控日余量）。

### 3.2 账本（建议表）

`quota_ledger`（名可再定）每条至少含：

- `user_id`（可空 = 系统/公共）
- `action`、`scope`（如 `date` / `league_id` / `fixture_id`）
- `estimated_requests` / `actual_requests`（若可知）
- `status`：`accepted` / `denied` / `deduped`（命中 running 或已新鲜未打官方）
- `created_at`

用户侧日汇总：`user_quota_daily(user_id, day, used, limit, plan)`。

### 3.3 扣费规则（建议）

1. 请求进入需打官方的路径前：`can_spend(user, action, cost)`。  
2. 若全局已有同类 sync `running` → 返回现有 `running`，记 `deduped`，**不扣**或扣「触发尝试」的极低成本（产品二选一，推荐不扣）。  
3. 若本地已满足 TTL / 已有初盘且策略为「只补缺」→ 可不打官方，不扣或少扣。  
4. 真正发起官方 HTTP 前扣减（或预留 + 完成后结算），失败可回滚预留。  
5. 额度用尽：HTTP `402` 或 `429` + 业务码 `quota_exhausted`；前端提示「本地仍可用，无法再向官方拉取」。

## 4. 鉴权与会话

### 4.1 现状

- 前端：`LoginModal` 对接 `/auth/register`、`/auth/login`；不持有 token，只缓存用户名用于首屏渲染，`api/client.ts` 开 `withCredentials`。  
- 账号：用户名或**邮箱**（含 `@` 时归一为小写后入库与比对，真源 `auth.normalize_account`）。  
- 后端：`users` + `user_sessions`（30 天 opaque token）；token 只走 **httpOnly cookie**（`fa_session`）；收藏/方案按 `user_id` 隔离；游客桶 `user_id=""`。  
- 运维：`users.is_admin`（非 VIP）；「我的 → 管理员设置」仅管理员可见；`/admin/*` 认会话 `is_admin`，兼容 `X-Admin-Key` 给脚本。授予：`python manage.py set-admin <账号>`；取消：`python manage.py unset-admin <账号>`。  
- 首登认领：登录/注册时把游客桶**手动收藏**与**方案**迁到账号；`source=auto` 每日推荐留在游客桶，登录后列表合并可见。  
- 官方 Key：只用管理员库内配置（见 [API_SPORTS_KEYS.md](./API_SPORTS_KEYS.md)）。

### 4.2 密码与传输（已定，勿再改方案）

| 约定 | 说明 |
|------|------|
| 落库 | 只存 `users.password_hash`：PBKDF2-SHA256、120000 轮、每用户随机盐，格式 `salt$hex`（真源 `auth.hash_password`） |
| 传输 | 请求体明文 + **TLS**；生产必须走 HTTPS（反代终止 TLS，建议加 HSTS），公网禁止 http |
| 前端预哈希 | **禁止**（含 MD5/SHA 等）。MD5 不可逆、无「后端解密」可言；把哈希值当密码比对等于换个名字的明文，抓包即可重放，还削平口令熵、焊死算法升级路径 |
| 会话载体 | **httpOnly + SameSite=Lax cookie**（`fa_session`）；生产置 `SESSION_COOKIE_SECURE=true`。不存 `localStorage`，页面脚本读不到 → XSS 偷不走会话 |
| CORS | `CORS_ALLOW_ORIGINS` 显式白名单 + `allow_credentials`；cookie 鉴权下**不得**用 `*` |
| 日志 / 响应 | 原始密码不进日志；token 不进任何响应体；`/auth/*` 只回 `id`、`username`、`claimed` |

DevTools 的 Network 面板挂在 TLS 之上，展示的是加密**之前**的请求体 —— HTTPS 站点在面板里同样是明文，这不是缺陷，勿据此改成前端加密。本地 dev 走 `http://localhost`（回环、不出本机）。

### 4.3 目标形态（VIP 尚未实现）

- VIP：`user_entitlements` 或 `subscriptions`（`plan`、`expires_at`）。  
- 不提供用户官方同步路由；列表和已落库详情可继续匿名只读。

密钥规范遵循现有 secrets 规则；生产再定 OAuth（可选，非必须首版）。

### 4.4 用户私有数据

收藏、计算器方案等**按用户隔离**；游客与登录共用本地库时靠 `user_id` 分桶。

| 约定 | 说明 |
|------|------|
| 游客桶 | `user_id=""`（空串，非 SQL NULL），仅承载共享的 `source=auto` 每日推荐；兼容 SQLite 复合主键 |
| 查询必带作用域 | `owner_is` / `normalize_owner_id`；登录用户收藏列表额外合并游客桶 `source=auto` |
| 鉴权依赖 | `CurrentUserId` 解析 `fa_session` cookie（可空）；写操作走 `RequiredUserId`，无效/缺失 → **401 请先登录** |
| 私有写操作 | `/favorites` POST/DELETE、`/bet-plans` 全部方法均要求登录；前端未登录先弹登录窗 |
| 登出清缓存 | 清账号侧客户端缓存：`fa-auth-user`、方案 session 缓存 / 遗留 localStorage、内存收藏与方案、计算器选单；**保留**主题、联赛勾选、记住账号、日期条、滚动位置 |
| 首登迁移 | 注册/登录时 `claim_anonymous_private_data`：认领历史游客桶里的手动收藏 + 方案；auto 不认领 |
| 收藏 PK | `(user_id, fixture_id)` |

已挂钩的表/接口：`favorite_fixtures.user_id`、`bet_plans.user_id`，以及 `/favorites`、`/bet-plans`、`/auth/*`。

**原则**：未登录时**不假装**做云同步或跨设备私有；私有写路径必须过 `RequiredUserId`；【关注】只返回当前账号的手动星标，公共自动推荐走独立只读接口。

## 5. 与现有同步链路的对齐

| 现网行为 | VIP 方案下 |
|----------|------------|
| 打开 / F5 / 下拉刷新 | 只重读本地库 |
| 勾选非热门联赛 | 只改变本地筛选，不补拉盘口 |
| 详情（当前、VIP 未落地） | 免费配额开启时所有用户均可打开，但完全只读本地公共数据；关闭后热门联赛缺包可按需补拉并落库 |
| 详情（后续 VIP） | 游客 / 普通账户只浏览【比赛】列表公共数据，不进入全量详情；VIP 才可查看完整盘口、交锋、近况、阵容、伤病与简报。VIP 的官方补拉必须走独立权益与预算控制，不能无上限放大公共免费池 |
| 定时 00/06/11/16/19/22 | 公共池同步赛程/热门勾选盘口/赛果；积分榜**只刷新热门勾选**（其它联赛只读本地、不烧官方配额） |
| 全量详情预拉 | 独立开关已移除；已订阅完整批次仅 enrich 今天/明天热门未开赛缺包场次，配额耗尽即停；未订阅不预拉 |
| 初盘冻结 / 即时盘展示去重 | 数据语义不变；与鉴权正交 |

**固定边界**：列表不触发官方；免费配额下详情也不触发官方；详情补拉结果落库共享。用户身份与 VIP 不改变固定批次频率。VIP 权益落地前不提前拦截普通用户详情；落地后再将全量详情权限收口到 VIP。

## 8. 风险与约束

| 风险 | 应对 |
|------|------|
| 固定批次超出官方日配额 | 监控每批消耗与官方日余量，按需缩小盘口预算 |
| 用户以为「VIP=实时比分」 | 文案与产品边界写清：赛前分析，非直播 |
| 调度失败导致数据偏旧 | 页面继续读最近版本；任务状态与日志明确失败批次 |
| 在线用户过多拖垮后端 | 只增加本地读压力，不放大官方请求 |

## 9. 验收标准（本方案「完成」时）

- [ ] 列表 / F5 / 筛选入口均不触发官方 API
- [ ] 每天只注册六个固定赛程/盘口/赛果批次；全量详情预拉默认关
- [ ] 免费配额下详情零官方请求；关闭后或未来 VIP 独立额度允许时，详情缺包才按需补拉并落库
- [ ] VIP 与免费权益不提供「手动刷官方」入口
- [ ] 平台日志能回答每批消耗与剩余配额
- [ ] Key 仍仅存后端；前端无官方 Key
